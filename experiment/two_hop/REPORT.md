# two-hop 跨 GPU 传输实验（共享 host 内存，去掉 worker memcpy）

测量日期 2026-09-28。硬件：2× RTX 5090（驱动 576.88，PCIe x8/x8），Windows 11，
Vulkan SDK 1.4.350。代码基线：`21e74e0`（`experiment/v5/` 与所有 shader 零改动，
`git status experiment/v5` 为空）。

## 0. 结论

| 区间 | 结果 | 依据 |
|---|---|---|
| 生产配置，1M–16M | **无差别**：two-hop / three-hop = 99.82 %–100.34 % | §4.1，每点 3 个交错 trial |
| 生产配置，5 万–50 万 | **two-hop 快 0.5 %–1.4 %** | §4.2，每点 5 个交错 trial |
| 传输链真正暴露时（旧配置，1M / 2M） | **two-hop 快 29 % / 15 %** | §4.3，非生产配置，仅作敏感性对照 |
| 更慢 | **未观察到**。最大负偏差 −0.18 %（2M），低于 3 个 trial 能分辨的量级 | §4.1 |

三句话：

1. **Step 0 通过。** 两张 5090 能导入同一块 host 内存，双向逐字节正确，共享块的 DMA
   速率与 v5 现有 staging 相同（约 28.5 GB/s）。
2. **在当前 v5 campaign 配置下没有"传输暴露区"。** spec 假设 1M–4M 暴露，实测
   三跳基线的 `b_to_c_gap` 从 5 万到 1600 万粒子中位数都是约 6 µs。two-hop 省下的
   memcpy（104–411 µs）全部变成了 upload 到 phase C 之间的余量，不改变帧时间。
3. **担心的耦合没有出现。** `consumed` 挪到 `upload_done` 之后，没有推迟下一帧的
   readback（§6）。所以 Step 1b 没有做（§7）。

附带发现（与 two-hop 无关，见 §4.4）：本机 K=2 下 `V5_CASCADE_FORCE=0` 对两种传输
都更快，1M 约 +4.7 %。

**第二轮（§12）把范围推到 10k。** 主配置下结论不变：中位数帧从不暴露，差别
≤ 1.5 %。但关掉 cascading force 后，三跳在 200k 及以下暴露，two-hop 快
2.5 %–5.6 %。

| 1 MiB | a / b | 37.0 / 37.2 | 37.2 / 37.2 | 37.3 / 37.3 | 37.3 / 37.3 |
| 4 MiB | a / b | 147.0 / 147.0 | 146.9 / 146.8 | 146.6 / 146.3 | 146.5 / 146.8 |

## 2. 实现

| 文件 | 内容 |
|---|---|
| `shared_host_v5.py` | `VulkanContextTwoHop`、host 分配与导入、`SharedHostLinkPool`、`SphSimulatorTwoHop`、`GhostRelayWorker`、`ChainOrchestratorTwoHop` |
| `probe_shared_host.py` | Step 0 探针 |
| `_run_two_hop_bench.py` | 唯一的 runner，`--transport {three_hop,two_hop}` |
| `_run_two_hop_campaign.py` | 测量矩阵：交错 trial + instrumented 运行，每次运行一个新进程 |
| `_summarize_two_hop.py` | 汇总表 |
| `_run_two_hop_equivalence.py` | 数值等价性（包络法） |

**共享块注入。** 先有共享块，再构造 sim。`SharedHostLinkPool` 在两个 context 建好后
创建；`SphSimulatorTwoHop` 只覆写 `_allocate_staging_buffers`，向池按
（左 slab 序号，流向）取块，先到的一端分配，后到的一端拿到同一指针，各自导入。
`_Buffer.mapped` 置 `None`，v5 的 `destroy()` 因此只释放导入句柄；`mapped_view`
切到恰好 `total` 字节，因为 worker 在视图末 4 字节读 frame stamp。

**`consumed` 的位置。** relay worker 每帧的顺序：

```
1a wait source readback_done(n)
1b wait dest   readback_done(n)          （host signal 单调性保护，原样）
1c wait dest   upload_done(n-1)          （保留，但已不起保护作用）
   stamp 检查
3  signal dest worker_done(n)            → 放行 upload(n)
4  wait dest   upload_done(n)            ← 新增
   stamp 复查：必须仍等于第一次读到的值    ← 新增
5  signal source consumed(n)             ← 从 memcpy 之后挪到这里
```

第 4 步用的是现有接口 `dest.sync.dest_upload_guard_ops(direction, n+1)`，没有改
sync scheme。aggregated scheme 下这个接口返回空，所以 two-hop 只接受
`per-direction`，构造时检查。

## 3. 测量方法

- **同一个 runner。** 两臂只有 `--transport` 不同。K=2 `ChainPartition`，
  `--weights 1.0,1.0`，`--sync-scheme per-direction`，`--pool-safety 1.2`，
  `--warmup 1000 --max-steps 3000`（小规模组是 2000 / 12000）。
- **环境变量**由 runner 在导入 v5 之前固定：`V5_WORKER_COUNT_AWARE=1
  V5_GHOST_POOL_FACTOR=0.25 V5_SPLIT_TRANSFER_QUEUES=1 V5_CASCADE_FORCE=1
  V5_BAND_VOXEL_DISPATCH=1`。所有运行都关闭 validation 层。
- **fps**：`run_pipelined` depth 2，不挂 GPU 计时器，每个 trial 一个新进程，
  顺序 three, two, three, two, …。
- **GPU 侧分段**：每个 (case, transport) 另跑一次 `--instrumented`，同步 depth 1，
  逐帧读 compute 与 transfer 两个 query pool。
- **worker 分段**：host 时间戳，每次运行每帧都有。
- **每次运行结束**：最终 defrag、alive 守恒、GPU 与 host 的 stamp 错误计数、
  upload 期间覆盖计数、seam 完整性检查。

与 spec 的两处出入，动手前已说明：

1. runner 以 `_run_v5_chain_bench.py` 为模板，不是 `_run_v5_dual_bench.py`。后者是
   同步 depth 1，没有 `--depth` 和 `--seam-check`。
2. depth 2 下拿不到逐帧的 `b_to_c_gap`（在途的帧会覆盖 query slot），所以
   `b_to_c_gap` 和 upload→C slack 来自 depth 1 的 instrumented 运行。

读数时要注意：

- 跨 pool 的差值（readback sched gap、upload→C slack）按 v5 2026-07-22 的审计
  结论属于"该驱动上的经验观察"，同 pool 的差值才是严格的。
- 不同组是在不同时刻跑的，绝对 fps 有最多约 2 % 的组间漂移（例如三跳 100k：小规模组
  1476，loop trace 组 1505–1512）。**只有同组内交错的两臂可以直接比。**
- 每点 3 或 5 个 trial，表里给的是极差，不是置信区间。

## 5. 机制：三档各自对应什么

**更快 —— 链暴露（§4.3 的 1M、2M）。** phase C 在等 upload。三跳的链是
readback 调度间隔 + readback DMA + worker copy + upload DMA，copy 占 412 / 581 µs。
two-hop 去掉 copy，链回到 phase B 之内。worker 分段里能直接看到：`copy` 从
412 µs 变成 0.8 µs，`b_to_c_gap` 从 390 µs 变成 6 µs。

**无差别 —— 链藏住（§4.1 全部，§4.4 全部，§4.3 的 4M）。** phase C 在等 phase B，
不在等 upload。copy 省掉的时间原样出现在 upload→C slack 里：

| case | 三跳 worker copy | slack 增量（two − three） |
|---|---:|---:|
| 1m | 104.4 | 104.8 |
| 2m | 143.2 | 145.4 |
| 4m | 203.7 | 197.3 |
| 8m | 285.8 | 269.4 |
| 16m | 410.6 | 357.7 |

**小幅更快 —— 中位数藏住、尾部暴露（§4.2）。** 余量薄到与 worker 线程的调度抖动
同量级时，多出来的余量减少了暴露帧的比例。

**更慢 —— 未观察到。** 两个可能的来源都查过：

- 耦合（§6）：没有发生。
- upload DMA：two-hop 下稳定长 2–10 µs（4 %–14 %，例如 16M 200.6 → 210.6）。
  空载探针里没有这个差别，原因没有定位。它落在余量里，不影响帧时间。

## 6. `consumed` 耦合对 `b_to_c_gap` 的影响

耦合的内容：two-hop 下，发送卡的 readback(n+1) 要等接收卡的 upload(n) 读完，而且
这个许可经过 host 线程（`vkWaitSemaphores` 返回，再 `vkSignalSemaphore`）。

测到的：

| 证据 | 三跳 | two-hop |
|---|---|---|
| readback 调度间隔（ghost_send 结束到 readback DMA 开始），1M–16M | 41.7–44.0 µs | 42.4–44.2 µs |
| 同上，5 万–50 万 | 39.7–41.6 µs | 39.9–41.3 µs |
| `b_to_c_gap` p50，全部生产配置点 | 5.8–6.1 µs | 5.4–5.9 µs |
| worker 从 `upload_done` 到发出 `consumed` | — | 5.5–7.7 µs |

如果门控卡住过 readback，readback 调度间隔会变长。两臂相同。

余量（two-hop，depth 2）：worker 处理第 n+1 帧时等 `readback_done(n+1)` 的时间，
近似等于 `consumed(n)` 发出到 readback(n+1) 完成的间隔。

| case | p50 | p1 | readback DMA |
|---|---:|---:|---:|
| 50k | 511.2 | 325.7 | 9.3 |
| 100k | 521.7 | 335.4 | 12.5 |
| 250k | 578.8 | 368.2 | 17.7 |
| 500k | 736.7 | 409.4 | 24.4 |
| 1m | 1077.1 | 439.7 | 38.4 |
| 2m | 1791.9 | 553.0 | 55.8 |
| 4m | 3690.6 | 715.5 | 86.1 |
| 8m | 6938.6 | 1099.5 | 128.4 |
| 16m | 13297.1 | 1772.3 | 186.5 |

单位 µs。99 % 的帧里，门在 readback(n+1) 完成前至少 325 µs 就已经打开。剩下约
0.5 % 的帧这个读数只有几 µs，但它们在两种传输里出现在**相同的帧号**上（1M
trial 0：每千帧里的第 8、21、30、44、45、349、371、690、712 帧）。三跳没有这个
门控，所以这些帧不是门控造成的；具体原因没有查。

原因是结构性的：对称 K=2 下，发送卡自己要先等到自己的 upload(n)，再跑完
phase C(n) 和 phase A(n+1)，才轮到 readback(n+1)。接收卡的 upload(n) 与它几乎
同时完成。

**不成立的情形**：两张卡负载明显不对称，或 K>2（见 §9）。

1c 的说明：two-hop 下共享块的写入者是发送卡的 readback DMA，worker 走到 1c 时它
已经写完，1c 不再保护任何东西。保护全部在 `consumed` 上，所以加了 upload 之后的
stamp 复查。全部 81 次 two-hop 运行（含冒烟和等价性）里复查失败 0 次。

## 8. 对照的公平性

**未改动的 v5 行为：**

- `experiment/v5/` 下所有文件、所有 shader。
- transfer 队列的选择，readback / upload 分两个 transfer 队列。
- timeline semaphore，`PerDirectionTimelineScheme` 的全部取值和 wait / signal 位置。
- phase A / B / C 命令录制，readback / upload 命令录制，13 个传输段。

- `ChainOrchestratorV5` 的帧循环（`run_pipelined`、`step`）、watchdog。

- partition、pool 大小、全部环境开关。
- 三跳一臂用的就是 `VulkanContextV5`、`SphSimulatorV5`、`ChainOrchestratorV5`、
  `GhostMigrationWorker` 本身。

**two-hop 一臂改动的：**

| 改动 | 说明 |
|---|---|
| staging 内存归属 | 每方向 2 块私有分配 → 1 块共享 host 内存，两端各自导入 |
| staging 内存类型 | 两端都是 `type[3]`（带 HOST_CACHED）；v5 的 receiver 是 `type[2]`。探针里两者 DMA 速率相同 |
| 设备扩展 | 多启用 `VK_KHR_external_memory`、`VK_EXT_external_memory_host`。§4.5 的对照显示不影响基线 |
| worker | 去掉 memcpy；`consumed` 挪到 `upload_done(n)` 之后；多一次 stamp 复查 |
| worker 构造 | 基类构造函数照常创建并启动 memcpy worker，随后停掉、一对一换成 relay worker |
| bootstrap 桥接 | `receiver_view[:] = sender_view` 变成同一块内存的自拷贝 |
| `V5_WORKER_AFFINITY` | relay worker 不处理。该变量只在 Linux 上有效，本实验未设置 |

## 9. 已知限制

- **只测了 K=2。** 接收端的 `upload_done` 聚合在 `main` 时间线上，由最后一个方向的
  upload 发出。K>2 时，中间节点会把左右两条链路通过这个信号耦合起来。要上 K>2，
  需要每方向独立的 upload 完成信号。
- **只支持 Windows。** host 分配用的是 `VirtualAlloc`。
- **depth 2 下没有 GPU 侧分段。** `b_to_c_gap`、slack、DMA 时间都来自 depth 1。
- **1M 点**用的是 spec 指定的 `cases/lid_driven_cavity_2d`（重调过参数的那个）。
  与 2M–16M 同族的 `lid_driven_cavity_2d_gen` 在 §4.2 里，结论相同。
- **流动未充分发展。** 3000 步的短测量；12 小时 soak 显示 8M 的稳态 fps 会随流动
  发展下降约 10 %。两臂受到的影响相同。
- **没有长时间稳定性数据。** two-hop 最长的一次运行是 12000 步。

## 12. 低负载扫描 10k–1M（第二轮）

测量日期 2026-09-28，21:08–22:04。约束同前：`experiment/v5/` 与 shader 零改动，
同一个 runner，两臂只有 `--transport` 不同。214 次运行（两臂各 107），drift 全为 0，
stamp 错误 0，upload 期间覆盖 0，install drop 0，seam 检查全过。

### 12.0 结论

**(1) 跳数从哪个负载开始产生可测差别。** 取决于 phase B 有多长，不单取决于粒子数。

| 配置 | 三跳的中位数帧 | two-hop / three-hop |
|---|---|---|
| 主配置（cascade on） | 10k–1M 全部藏住，`b_to_c_gap` p50 5.9–6.1 µs | 1M：100.0 %–100.4 %，极差重叠；500k 以下：100.4 %–101.5 % |
| cascade off | **≤ 200k 暴露**，gap p50 29–42 µs；≥ 500k 藏住 | ≤ 200k：102.5 %–105.6 %；500k：102.2 %；1M：101.2 % |

判据：三跳的链长加上约 37 µs（upload 完成到 phase C 启动的 semaphore 延迟）超过
phase B，中位数帧就暴露。主配置下 phase B 的下限是 251 µs，三跳的链在 10k 是
160 µs，永远够不着。cascade off 把 phase B 的下限降到 175 µs，三跳在 200k 及以下
就越线了；two-hop 的链短 25–53 µs，在所有负载下都还藏得住。

**(2) 差别来自哪一段。** host 段里的 worker copy。以 cascade off 的 100k 为例：
三跳链长 193.7 µs，two-hop 149.0 µs，差 44.7 µs；其中 copy 41.0 µs，外加 signal
段的 5.1 µs。两臂的 readback 调度间隔（40 µs）、readback DMA（12.5 µs）、upload
DMA（21–23 µs）相同。是延迟，不是带宽。

**(3) 低负载的 fps 上限是什么。** GPU 每次 dispatch 的固定开销，不是 CPU 提交、
DMA 或 semaphore 往返。10k 下 phase A+B+C 合计 548 µs，占帧周期中位数 592 µs 的
92 %；六个邻域核每个 71–97 µs，与粒子数几乎无关。CPU 提交中位数 70 µs，与 GPU
并行执行；主线程在 99.9 % 的帧上都在等 GPU；depth 3 的 fps 与 depth 2 相同。

附带结论：

- **cascade off + two-hop 是这台机器上低负载最快的组合**，相对现在的生产配置
  （cascade on + 三跳）：10k–100k 约 +10 %，200k +5.4 %，500k +3.8 %，1M +2.4 %。
  这是跨组比较，见 §12.7。
- 只关 cascade、保留三跳：10k–100k 有 +4 %–+8 %，但 200k 是 −0.1 %：省下的一次
  dispatch 被暴露的传输链吃掉了。

几个量的定义：

- **CPU 提交**：v5 默认的 `run_pipelined` 循环不调用 `_submit_sim_frame`，每帧的
  提交走 `_submit_frame`（两个 sim 的全部提交加 worker 通知）。计时用的是 v5 自带的
  `V5_LOOP_TRACE=1`，取 warmup 之后的逐帧数据。
- **无等待帧**：主线程去等 frame_done 时该帧已经完成（等待 < 5 µs）的帧占比。
  接近 100 % 才是 CPU 在定节拍。
- **链长**：本卡 phase A 结束到入站 upload 落地的时间，
  = `a_to_b_gap` + phase B + `b_to_c_gap` − upload→C slack。
- **host 段**：链长减去 readback 调度间隔、readback DMA、upload DMA。里面是
  semaphore 往返、host 线程唤醒，以及三跳的字节拷贝。readback 两段用的是本卡自己的
  读数代替对端的（K=2，等权重）。
- depth 2 下每 1000 帧才有一次 GPU 时间戳，采样数不到 200，所以 GPU 列都来自另跑的
  depth 1 逐帧 anatomy；fps 以 depth 2 为准。

### 12.7 读数时要注意

- **cascade on 与 off 是两个组**，分别在 21:08–21:31 和 21:31–22:04 测的，不是交错
  测量。§12.3 里跨组的百分比受组间漂移影响，第一轮估计这个漂移最多约 2 %。
  ≤ 100k 的 +4 %–+10 % 超出这个量级，500k 和 1M 的 +1 %–+4 % 不一定。
  同一组内 two-hop 对三跳的比较是交错测的，不受影响。
- **与第一轮的绝对 fps 不能直接比。** 步数不同（例如 100k：12000 对 21000），
  切换间隔不同，本轮开了循环计时。100k 三跳：第一轮 1476，本轮 1440。
- **尾部统计在不同时段之间会变。** 100k 三跳暴露帧（> 20 µs）：第一轮 9.0 %，
  本轮 12.9 %（0.2 ms）和 15.2 %（5 ms）。1M 三跳：第一轮 0.5 %，本轮 3.4 %–3.9 %。
  原因没有查。同组内两臂是前后脚测的，对比仍然成立。
- **§4.4 需要修正。** 第一轮在 `1m` 上用 3 个 trial 测得 cascade off 下 two-hop 对
  三跳是 100.30 %，极差重叠，当时记为无差别。本轮在 `1m_gen` 上用 5 个 trial 测得
  101.16 %，极差不重叠。
- **1M 的测量窗口只有 2.6 s**，其余各点 ≥ 12 s。
- **upload 完成到 phase C 启动的 37 µs** 是从链暴露时的 slack 中位数读出来的，
  是跨 query pool 的差值，属于该驱动上的经验观察。
- 只测了 K=2、本机、2-D 方腔。cascade off 的结论没有在 K>2 或集群上验证。
