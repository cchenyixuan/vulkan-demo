3. **两个轻负载点（每卡约 2M）是多模态的，它们的 η 不能当作设计本身的效率：**

   - 这两点的“两臂差”在 −29 % 到 +107 % 之间，是噪声，不是臂的效果。
4. **原因（新发现）：集群上传输 worker 的唤醒偶尔晚约 10 ms，而且只在两个线程同时等同一个信号量值时发生。**
   - 链路 a→b 的 worker 每步做两次阻塞等待，都用无限超时的 `vkWaitSemaphores`。第一次等源端 a 的 readback。第二次是 dest guard，等 b 自己同一步 b→a 方向的 readback。第二次等的这个值，恰好也是反向链路 b→a 的 worker 第一次在等的值。
   - 16 条 trace 里共有 11.6 万次阻塞的 dest guard，其中 17.7 % 晚到 5 ms 以上。**每一次迟到都发生在反向 worker 同时睡在同一个值上的时候。** 单独等待的 dest guard 有 318 次，没有一次迟到。同时在等的那个反向源端等待几乎总是准时：K = 8 的 8.3 万次里一次也没迟到，K ≤ 4 的 3.3 万次里迟到 0.4 %。
   - 如果等待是在信号前不到 10 ms 开始的，它会在开始后正好 10.06 ms 返回（p01 10.058 ms）。这像是唤醒被漏掉，再由驱动内部大约 10 ms 一次的复查兜底。我们的代码用的是无限超时，所以这 10 ms 不来自我们的代码。本机 Windows 的 trace 里没有一次迟到。
   - **代价取决于负载。** 2-D 每卡 ≥ 8M 和所有 3-D 点上它被完全隐藏：迟到的那些步并不更长。每卡 2M 时，按 trace 估算“每一步都准时”的步长，K = 2 的步长被拉长 14–16 %，K = 8 的被拉长 23–29 %；多模态也来自这里。
   - 剩下的 43 个点里，有 21 个是每卡 ≤ 4M 的 2-D 点，会受影响。它们主要是 F7 小规模族，以及 F1 和 F3 里的轻点。另有 1 个 3-D 点（F8 3d_n200_x96，每卡 2.25M）处在边界。
5. **两臂：** 2-D 重负载点上 C 臂比 E 臂平均快 0.6–1.5 %，每次试验都更快（0.4–1.8 %）。3-D 在 K = 4 时 C 快 0.5 %，在 K = 8 时 C 慢 0.3 %。K = 8 时 3-D 一个 slab 只有约 41 列，校准每次只能挪 1 列（约 2.4 %），分辨率不够。

### 4.1 迟到的唤醒

分析工具是 `docs/cluster_v6/scripts/e7_late_wake.py`，全部输出在 `data/e7/batch1/late_wake_b1.txt`。只统计真正阻塞过的等待。迟到的定义是：GPU 的 readback_end（按拟合后的主机时钟）之后超过 5 ms 才醒。

**它发生在哪里。**
- 迟到的几乎都是 dest guard，即等接收端 b 自己 b→a 方向那一步 readback 的那次等待。
- 源端等待（等发送端 readback）几乎不迟到。
- K ≥ 4 时，迟到主要落在“向左”的链路上，即 s(k+1)→s(k)；K = 2 时两条链路都有。

**两个线程等同一个值（16 条 trace 合计）：**

| 阻塞的 dest guard | 次数 | 迟到 |
|---|---|---|
| 反向 worker 的源端等待同时睡在同一个值上 | 116,180 | 20,656（17.8 %；各 trace 10–28 %） |
| 单独等待 | 318 | 0 |

- 这是观察性的比较，不是随机对照：单独等待的 318 次里有 292 次来自 2d_n4000 K8，那里共享等待的迟到率是 17–23 %。即使只按 10 % 的迟到率算，318 次全部准时的概率也小于 10⁻¹⁴。
- 同时在等的那个反向源端等待：K = 8 的 83,217 次里迟到 0 次；K ≤ 4 的 32,963 次里迟到 139 次（0.4 %）。

**它要等多久。**
- 在信号前不到 10 ms 开始的等待，迟到时在开始后 10.06 ms 返回。例如 2d_n4000 K8 E 臂的 1426 次迟到里，1138 次落在 10.00–10.25 ms 这一格，p01 是 10.058 ms。
- 开始得更早的等待，返回点落在 10 ms 的倍数附近。例如 3-D K = 8 有一团在 29.75–30.0 ms。
- 我们的代码对这两次等待都用无限超时（`transport_v7.py` 的 `_run`，`simulator_v7.wait_semaphore`），所以 10 ms 来自驱动或内核内部。
- 本机 Windows 的 trace 里没有一次迟到。

**代价（同一条 trace 里，有迟到的步和准时的步分开比）：**

| 点 | 每卡 | 迟到占阻塞 dest guard 的比例（E / C） | 步长：全部 / 准时步 / 迟到步（µs，E 臂） | 若每步都准时 |
|---|---|---|---|---|
| 2d_n1440_k2 K2 | 2.1M | 11.5 % / 11.7 % | 3771 / 3181 / 8493 | 步长短 14–16 %（E 314 对实测 265 fps） |
| 2d_n4000 K8 | 2.0M | 16.8 % / 23.2 % | 6825 / 4863 / 8606 | 步长短 23–29 %（E 206 对实测 147 fps，C 148 对 115） |
| 2d_n2840_k4 K4 | 8.1M | 15.9 % / 19.1 % | 11072 / 11196 / 10934 | 无差别 |
| 2d_n8000 K8 | 8.0M | 23.3 % / 22.8 % | 11129 / 11343 / 11083 | 无差别 |
| 2d_n8000 K4 | 16.1M | 10.3 % / 26.3 % | 21263 / 21306 / 21166 | 无差别 |
| 2d_n11320 K8 | 16.1M | 16.2 % / 11.4 % | 20847 / 20633 / 20913 | 无差别（±1 %） |
| 3d_n160_k8 K4 | 9.1M | 14.3 % / 17.3 % | 64199 / 65414 / 62476 | 无差别 |
| 3d_n160_k8 K8 | 4.5M | 20.6 % / 9.9 % | 32249 / 32913 / 32062 | 无差别 |

- **轻负载点上，迟到直接拉长步长。** 每卡 2M 时，有迟到的那些步上，接收端在 phase B 结束后要等 7.6–8.5 ms 才能开始 phase C。准时的步平均只等 0.2–5.3 ms，这个间隔里还包含相邻链路传过来的迟到。
- **重负载点上，迟到被藏在 phase B 里。** 2-D 每卡 8M 时，有迟到的步上这个间隔是 0.1–1.1 ms，迟到的步并不更长。16M 和 3-D 时这个间隔基本是 0。
- **这是轻负载多模态的直接机制。** 每次运行里，迟到集中在哪几条链路、发生得多频繁并不一样（例如 2d_n4000 K8 E 臂在 s4→s3，C 臂在 s7→s6），所以整次运行的 fps 会分成几团。
- **它不解释重负载点的 η。** 2d_n8000 K = 8 的 0.91 和 K = 4 的 0.97 之差另有来源。按 E29 的分解，更可能是每卡负载减半后，phase C/A 和步间间隔占的比例变大。这要由第 4 批的 anatomy 点来确认。

## 11. 需要你决定的事

**唤醒问题怎么处理（影响第 2、4 批里 21 个轻负载点，第 3 批不受影响）：**

- **A. 不改代码，按计划用 rc1 跑完。**
  - 轻负载点会像批次 1 一样多模态，η 主要反映这个约 10 ms 的问题。报告照实写，并附上机制。
  - 代价：F7 小规模曲线和 F1/F3 的轻点基本只能当作“平台现象”使用。
- **B. 先修再跑。** 只改主机端的等待方式，不动数值。有两种做法：
  - **B1，有界等待。** dest guard 改成短超时（例如 0.1–0.2 ms）的 `vkWaitSemaphores` 循环，超时后重新检查。改动最小，迟到被限制在超时长度以内。
  - **B2，每个值只留一个主机等待者。** 反向 worker 的源端等待返回后，在主机端记下“b 的 readback_done(n) 已到”，dest guard 改为等这个主机事件。这从结构上去掉了数据所指向的条件，但改动多一些，停止路径也要处理。
  - **验证方案：**
    - 本机：逐位一致 + trace。本机本来就没有迟到，所以只能验证正确性和没有退步。
    - 集群：一个小作业，约 0.5 node-h。重跑 2d_n4000 K8、2d_n1440_k2 K2 和一个重负载点，各带 trace，确认迟到消失、多模态消失、重负载点不变。
    - 通过后打 `v7-rc2`。批次 1 的两个轻负载点用 rc2 重跑，约 0.45 node-h，放进第 2 批。
    - 重负载点保留 rc1 的数据，因为迟到在那里被隐藏，修复从构造上不改变它们。第 4 批的跨节点重复点可以顺带核对 rc1 和 rc2。
- **C. 折中（我的建议）。** 现在用 rc1 开第 3 批：7.7 node-h，全是每卡 ≥ 4.5M 的 3-D 点，批次 1 已证实迟到在 3-D 上被完全隐藏。同时按 B1 做修复和验证。第 2、4 批等修复通过后再开。

**其他：**
- 下一批的作业脚本按重拟合模型重新生成时间上限（默认这样做，除非你反对）。
- socket 1 起步慢只花节点时间。要查原因需要单独的小测试，我建议放到 E7 之后。
