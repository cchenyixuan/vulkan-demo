## 2. 机制复现（第 1–3 条）

**程序与作业。**
- 程序：`docs/cluster_v6/scripts/e7_wake_repro.py`，不含求解器代码。
- 和求解器用同一套绑定：`vulkan` 包（cffi）、原始 `vkWaitSemaphores`，每次调用新建小结构体。
- 线程方式也相同：等待者是 `threading.Thread`，GIL 切换间隔 0.2 ms。
- 信号有两种来源：
  - GPU：在专用传输队列上提交 `vkQueueSubmit2`。命令缓冲先把 1 MiB 从设备拷到主机，再写一个 bottom-of-pipe 时间戳，然后发信号。
  - 主机：`vkSignalSemaphore`。
- 每次迭代：
  - 所有等待线程同时放行，各自记下开始时间，然后等本次的值；
  - 随机延迟 0.2–3 ms 后，主线程发信号；
  - 延迟 = 等待返回时刻 − 信号时刻。GPU 信号的时刻取上面那个时间戳，经 calibrated timestamps 换到主机时钟；
  - 只统计信号前就开始的等待（“阻塞”）。迟到的定义是信号后 5 ms 以上才返回。
- 负载线程模拟主循环：在每 1 ms 的窗口里，有 50 % 的时间跑 Python。它每忙 1 s 完成的工作量，与没有等待者时相比，就是等待者的 GIL 代价。
- 作业 1691733，节点 wqd10nah09g5（批次 3 B 刚用过的整机）。进程绑在所测那张卡所在 NUMA 节点的 CPU 上。
  - GPU 0（socket 0）：35 种情况（33 种有等待者，加首尾两次无等待者的基准），每种 4000 次迭代（longwait 1000 次），用时 13.9 min。
  - GPU 4（socket 1）：6 种情况的短测，每种 2000 次，用时 1.4 min。
- 第一次提交（1684054）分到了还丢着 GPU 1 的 wqd10nah10g2，在打开设备时卡住，没有结果（见 1.6）。

两个线程等同一个信号量时每次等待从开始到返回的时间（GPU 信号，有负载，GPU 0，各 8000 次等待，每格 0.25 ms），数据在 `hist_return_from_start_gpu0.json`：rc1 的做法有一半在开始后 10.0–10.5 ms 才返回；rc2 的做法（一个线程睡、另一个等转告）没有一次超过 5 ms。

**规律：**
- **每次信号只叫醒一个线程。** 同一个时间线信号量上有 n 个线程阻塞在无限超时的 `vkWaitSemaphores` 里，GPU 发信号时，每次迭代恰好 1 个按时醒来，其余 n − 1 个迟到。4000 次迭代里没有一次例外。
- **迟到的线程靠驱动内部约 10 ms 一次的复查醒来。** 迟到者在各自开始等待后 10.08–10.21 ms 返回（有负载时 10.09–10.37 ms，多出的是抢 GIL 的时间）。GPU 信号、无限超时的情形（不含 longwait）一共 63,221 次迟到，全部在开始后 8.2–10.6 ms 返回。开始得更早的等待落在 10 ms 的倍数上：longwait 情形的等待在信号前约 15 ms 开始，迟到者在开始后 20.2–30.5 ms 返回，集中在 20.0 和 30.0–30.25 ms 两格。
- **10 ms 不是内核节拍。** 两台节点都是 CONFIG_HZ=250，即 4 ms 一拍（见 2.3）。我们的代码用无限超时，所以这个 10 ms 来自驱动。
- **主机发信号时略有不同：** 约 5–8 % 的迭代里所有等待者都迟到（无负载 5.2–5.5 %，有负载 7.6–7.7 %），单个等待者也有 2–3 % 迟到，返回点不在 10 ms 上（中位数在开始后 8.8–9.3 ms）。求解器里没有主机线程等主机信号的值，所以不再展开。
- **批次 1 的迟到率比这里低**（共享阻塞的 dest guard 是 17.8 %，这里是 50 %）。机制相同，差别在等待开始得多早：
  - 漏掉唤醒的线程在它自己的下一个 10 ms 复查点返回。
  - 求解器里的等待常常在信号前很久就开始了（批次 3 的 3-D 点上，阻塞的 dest guard 合起来中位数等约 20 ms，在信号前约 14 ms 就开始；各 trace 的中位数是 10–214 ms，K ≥ 4 的点 10–20 ms，K = 2 的点 21–214 ms），下一个复查点只有大约一半的机会落在信号 5 ms 以后，所以只有约一半的漏唤醒被算作迟到。
  - 复现程序的等待（longwait 以外）都在信号前不到 5 ms 才开始：主线程随机延迟 0.2–3 ms 后发信号，GPU 信号的时刻还要再晚约 0.5 ms（提交加 1 MiB 拷贝），实测在等待开始后 0.2–4.7 ms。漏掉的一律算迟到。
  - 另外，求解器的模式（mixed）里有 19 % 的迭代根本没有漏唤醒。
- **本机 Windows（驱动 576.88）上同一程序不迟到。** 27 种情况、每种 300 次，0 次迟到。

### 2.2 哪些情形会触发（GPU 信号，有负载，GPU 0）

| 情形 | 做法 | 迟到 |
|---|---|---|
| distinct，2 / 4 个 | 每个等待者等同一信号量上**各自的值**，一次 GPU 信号同时满足所有值 | 50.00 % / 75.00 % |
| split，2 个 | 每个等待者等**各自的信号量**，同一次提交给两个都发信号 | **0** |
| mixed，2 个 | 求解器的模式：GPU 发奇数值，等待者 0 醒后用主机信号发下一个偶数值 | 40.5 % |
| stagger，2 个 | 等待者 k 晚 k × 间隔开始 | 49.9 %；迟到的几乎总是先开始的那个（3885 / 3989） |
| gpucompute，2 个 | 信号从计算队列发 | 50.00 % |
| cowait，1 个 | 主机 1 个等待者，**计算队列上同时有一个批在 GPU 上等同一个值** | **0** |
| cowait，2 个 | 同上，主机 2 个等待者 | 49.9 % |
| zeropoll，2 个 | 等待者 0 无限等；另一个每 100 µs 做一次零超时 `vkWaitSemaphores` | **0** |
| counterpoll，2 个 | 同上，但另一个用 `vkGetSemaphoreCounterValue` 查值 | **0** |

- 条件是**同一个信号量上有两个以上的主机线程在睡**。等的值相同还是不同、信号来自哪个队列、在哪个 socket 都不影响。各用各的信号量就没有问题（split）。
- **GPU 侧的等待不算第二个等待者**（cowait 1 个 = 0）。
- **不阻塞的检查不会抢走唤醒**（zeropoll、counterpoll = 0）。rc2 的计数器预检用的正是这两种调用。

## 3. 修法与验证（第 4–7 条）

### 3.1 dest guard 防的是什么（第 4 条）

链路 a→b 的 worker（记作 W_ab）在发出 worker_done(n) = 2n+2 之前，要等 b 在同一方向的传输时间线达到 b 自己的 readback_done(n) = 2n+1。这个等待防的不只是设备内存，一共三样：

1. **时间线的值序（显式）。** 主机发 2n+2 时，GPU 上的 2n+1 不能还挂着，否则违反 `VkSemaphoreSignalInfo` 的 value-03259（主机发的值必须小于任何还挂着的信号值）；GPU 的 2n+1 若在主机的 2n+2 之后才执行，时间线还会倒退（`VkSubmitInfo2` 的 semaphore-03882）。
2. **b 的 ghost 设备区（隐式）。** b 的 upload(n) 写入的设备字节，正是 b 的 ghost_send(n) 和 readback(n) 读出的那一段；在深度 2 下还包括 C(n−1) 读的那一段。upload(n) 只等 2n+2，所以“2n+2 在 2n+1 之后”就保证了 upload(n) 不会覆盖还没读完的数据。
3. **主机缓冲（隐式）。** 反向 worker W_ba 的源端等待条件是 b 的时间线 ≥ 2n+1。如果 2n+2 提前到了，这个等待会提前放行，W_ba 就会在 b 的 readback(n) 写完之前读 b.sender_staging。另外，dest guard 还隐含了 upload guard（b 的 upload_done(n−1)），从而保护 b.receiver_staging 不被 W_ab 提前覆盖。

所以它**不只防设备内存**。若改成 upload 提交时在 GPU 侧等待，需要同时做四件事：

- 新增一条只由主机发信号的 inbound[d] 时间线（worker 改在这条线上发信号）；
- transport 时间线改成只由 GPU 发信号；
- upload(n) 在 GPU 上同时等 inbound(n+1) 和 transport 2n+1；
- upload_done 改成按方向分开，否则 upload guard 会变成两个 worker 共享的阻塞等待，又造出同一种“两个等待者”。

对同一传输队列的影响：
- readback 在队列 0，upload 在队列 1（`V7_SPLIT_TRANSFER_QUEUES=1`，默认）。readback(n) 总在 upload(n) 之前提交，所以不会死锁。
- 队列 1 按提交顺序执行，前面的批在 GPU 上等信号时，后面的批也只能等。rc1 里已经是这样：同一接收端的两个入站 upload 各等自己 worker 的 worker_done(n)，排在后面的那个要等前面那个先跑完。批次 3 的 trace 里，这种排队在 K ≥ 3 的中间 GPU 上很常见。例如 3d_n200_k8 K=8 E 臂，s3→s2 的 upload 中位数要排 49 ms，因为排在它前面的 s1→s2 在等慢了一步的 s1（见 5.1）。这段排队不会推迟 phase C：phase C 反正要等两个 upload 都到。
- GPU 侧 dest guard 会让每个 upload 再等接收端自己的 readback(n)。两个入站 upload 本来都要在这一刻之后才开始，所以不会多出排队。变化只在于 upload 开始时少了一次主机唤醒。
- 这个做法会在同一个值上形成“一个主机等待 + 一个 GPU 等待”的组合：W_ba 在主机上等 2n+1，upload 批在 GPU 上也等 2n+1。复现程序的 cowait 情形测的就是这种组合，结果是 0 迟到（2.2 节）。

### 3.2 选哪一种（第 5 条）

**选 B2：单一等待者加主机端转告。** 这就是 rc2 候选 c56d078（`V7_DEST_GUARD=relay`，`V7_DEST_GUARD_PRECHECK=counter`，两者都是默认值），集群验证通过后打为 tag v7-rc2（3.4）。

| 做法 | 能否消掉迟到（复现） | 主循环负担（复现） | 改动 |
|---|---|---|---|
| GPU 侧等待 | 能：GPU 上等同一个值不算第二个等待者（cowait 1 个，0 / 4000） | 不增加 | 大：要同时做 3.1 的四件事，信号的归属和 upload 的等待条件都要改，GPU 协议要重新验证 |
| **B2 转告** | **能：52,000 次阻塞等待 0 次迟到** | **不增加：吞吐 95.5 %，单个等待者是 96.1 %，在噪声内** | 小：只改 worker 的 dest guard；GPU 协议、信号量、值和命令缓冲都和 rc1 相同，数值逐位相同 |
| B1 超时循环 | 能：76,000 次阻塞等待 0 次迟到 | 增加：每个等待线程 0.5–0.7 个核，主循环吞吐低 2–10 个百分点 | 小 |

GPU 侧等待和 B2 都满足标准。选 B2 是因为它改得少：它不碰 GPU 一侧，而且已经过了第 6 条的全部本机验证（3.3）。GPU 侧等待在主机关键路径上省掉的，只是一次 0.24–0.44 ms 的唤醒；按 1.4 的 trace，在重负载点上这段时间本来就被藏住了。

**rc2 怎么做：**
- 反向 worker W_ba 本来就在等 b 的 2n+1（它的源端等待）。等待返回后，它先把第 n 帧发布给一个 DestGuardRelay，再做自己的 dest guard。顺序是这样定的，所以两个 worker 不会互相等死。
- W_ab 的 dest guard 不再睡在信号量上：
  - 先用 `vkGetSemaphoreCounterValue` 查值。已经到了，就做一次零超时的 `vkWaitSemaphores` 作为正式的主机等待，然后继续。
  - 还没到，就等转告（Condition）。醒来后同样做那一次零超时等待。
- 于是每个传输时间线上只有 W_ba 一个线程在睡。复现程序表明，另一个线程查计数器或做零超时等待，不会抢走睡着的那个线程的唤醒（counterpoll、zeropoll 都是 0 迟到）。
- **失败路径：**
  - stop() 和 rc1 一样，先排空队列里的帧。
  - join 超时以后才释放转告。被转告卡住的 worker 改用 rc1 的阻塞等待，计为 fallback。
  - worker 死掉时，会中止它负责的转告。对方抛出 `DestGuardRelayAborted`，不会永远等下去。
- **可追溯：** 每个 worker 结束时打印一行 `dest guard: precheck N, relay M, fallback F, blocking B (relay slept S, released R; mode)`，step trace 的 run_meta 里也有这些计数。`V7_DEST_GUARD=wait` 可以恢复 rc1 的阻塞等待。
- **代价：** 转告交接让 dest guard 晚 20–75 µs 完成：本机 trace 里 p50 从 26–28 µs 变成 44–53 µs，复现程序里多 30–75 µs。重负载点上这段时间被 phase B 藏住；轻负载点上，它比一次 10 ms 的迟到小两个数量级。

## 4. 第 8 条：主机那一跳（memcpy）按 socket 分类

只用批次 1 已有的 16 条 trace。memcpy 这一跳 = worker_stamp → worker_copy，两个时间戳都来自 worker 线程自己的主机时钟。worker 绑在接收端 GPU 所在的 NUMA 节点上。GPU 0–3 在 socket 0，GPU 4–7 在 socket 1；K=8 的链里只有 s3↔s4 跨 socket。

**跨 socket 这一跳是否传到了 η 上**（按 trace 逐步做反事实估计）：

- 假设 s3↔s4 的 memcpy 只花 socket 0 的中位时间，它的 worker 就会早一点发信号，upload 也早一点开始。不过两个入站 upload 在同一条传输队列上按方向顺序执行，提前的 upload 仍要排在前一个后面。
- 按这个假设重算 s3、s4 的 phase C 开始时间，看能提前多少：

| 点 / 臂 | 多出的 memcpy（p50） | s3 / s4 的 phase C 平均晚开始 | 占步长 |

| 2d_n8000 C / E | 141, 111 / 83, 99 µs | 8.6, 4.1 / 24.0, 20.0 µs | 0.08, 0.04 / 0.22, 0.18 % |

- socket 1 内部的链路不比 socket 0 慢（0.90–1.02 倍），所以第 8 条的前提不成立：socket 1 上的链路没有明显更慢。
- 只有跨 socket 的 s3↔s4 慢 1.26–1.68 倍，每步多 83–335 µs。但这段时间几乎全被藏住：
  - 在 C 臂里，它让 phase C 平均晚开始 0–9 µs，不到步长的 0.1 %；
  - 在 E 臂里最多晚 24 µs（0.22 %）。

  - 卡住的是 s5 的入站数据。s5 分到 41 列，比 40 列的 slab 多 2.5 % 粒子；s1 也是 41 列。
  - s5 的 phase B 比 s4 长 1.2 ms，s4 和 s6 都在等它的 ghost 数据。

### 5.1 第 9 条的补充：r_chain 在 K ≥ 3 时仍含等待

按第 9 条换成 r_chain 以后，K ≥ 4 的重负载点 r_chain p50 多数仍有 0.5–1.0：批次 1 和 3 的 22 个臂里有 14 个，批次 3 的 10 个臂里有 9 个。例如 3d_n200_k8 K=8 E 臂是 0.997，3d_n200_k4 K=4 E 臂是 1.013。其余 8 个臂只有 0.03–0.34：批次 1 的 2d_n8000、2d_n2840_k4、3d_n160_k8 三个 K = 4 点的两臂，2d_n11320 K = 8 的 C 臂，3d_n160_k4 K = 4 的 E 臂。

这些点上传输本身的工作都很小：r_own 只有 0.02–0.10（3d_n416 是 0.37）。接收端 phase B 结束到 phase C 开始的间隔在多数 sim 上约 2 µs；但批次 3 的 10 条 K ≥ 4 trace 里有 5 条，最慢那个 sim 的这个间隔中位数超过 1 ms（最大是 3d_n200_k8 K=4 E 臂 s1 的 2.8 ms），批次 1 的 3d_n160_k8 K=8 C 臂 s4 是 1.3 ms，那里卡在等更慢的邻居（第 4 节）。

r_chain 偏高，是因为另有两段等待不属于“接收端的两次等待”，r_chain 没有扣掉：

1. **upload 在接收端的传输队列里排队。**
   - K ≥ 3 时，中间的 GPU 有两个入站 upload，在队列 1 上按提交顺序执行。
   - 排在前面的那个 upload，如果它的发送端慢了一步，就会在 GPU 上一直等自己 worker 的信号。排在后面的 upload 即使自己的 worker 早发了信号，也只能跟着等。
   - 例如 3d_n200_k4 K=4 E 臂：s0 比 s2 落后约一步，s2→s1 的 upload 中位数要排 50 ms。
2. **readback 等上一帧的 consumed 确认。**
   - readback(n) 要等本链路的 worker 读完第 n−1 帧的发送缓冲。
   - 那个 worker 若在第 n−1 帧的 dest guard 上迟到了，readback(n) 就跟着晚开始。
   - 例如 2d_n4000 K=8 C 臂的 s7→s6：readback 晚开始的中位数是 8.1 ms，那条链路的 dest guard 每步要等约 10 ms。

两者都是在等别的 GPU，不是传输本身的工作。所以汇总工具新增了 **r_own = t_own / T_B**：
- t_own 是 t_chain 减去 readback 和 upload 在各自传输队列上的“空等”时间，即从本批就绪到开始之间、队列上没有任何 DMA 在跑的那部分。
- 排在一个正在跑的 DMA 后面的时间不扣，因为同一队列上的串行本身就是传输工作。
- 实现在 `e7_full_summary.py` 的 `transfer_queue_idle`，合成测试 6 项全过。批次 1 的输出除了新增的字段外完全不变。
