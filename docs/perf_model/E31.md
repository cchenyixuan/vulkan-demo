## 结论

1. **切点:原因确认,已修。** 旧的 `compute_chain_cuts` 用 `searchsorted(side="left")` 的结果 k 作切点,左 slab 到第 k − 1 列为止,而第 k 列是第一个前缀达到目标的列,所以左 slab 总是少最多一整列(目标正好在列边界上时恰好少一列)。E29 的 9 个算例里目标都落在第 k 列的 70–90 % 处(生成器格点只部分填满第一个流体 voxel 列,两端不对称),所以 s0 几乎正好少一列;按初始状态算出的 n_B 与 E29 在 warmup 边界实测的 n_B 差不到 0.05 %。改成在 {k, k + 1} 里取前缀离目标更近的那个(等距取 k)后,K = 2 的流体偏差(最大 / 平均 − 1):3-D narrow 7.69 → 1.10 %、3-D 8M 3.48 → 0.50 %、2-D 10k 8.91 → 0.99 %、2-D 1M 0.90 → 0.10 %;3-D 1M 不变(2.97 %,一列就占半个 slab 的 7.9 %,两种规则切在同一列)。
2. **η 重测(不开仪器,3 次交替试验,K = 1 参照两卡同时)。** 3-D narrow **87.7 ± 1.6 %**(η_min 89.3 ± 1.6),3-D 8M **94.9 ± 0.4 %**(95.5 ± 0.4),2-D 1M **71.1 ± 0.7 %**(71.3 ± 0.6)。E29(旧切点,各一次,关仪器)是 85.5 / 92.0 / 70.8 %。K = 2 的 fps:narrow 46.11 ± 0.88(E29 44.95),8M 22.69 ± 0.05(21.59),2-D 1M 785.9 ± 7.4(774.0):2-D 1M 没有退化。旧切点这次没有重跑,两边相隔约 4 小时,差值带着本机几分钟内 ±1.5–2 % 的起伏,应以下面的等待变化为准。
3. **较快一侧在 B → C 的等待消失。** 3-D narrow:s0 的等待 p50 3,062 → 4.7 µs,周期平均 22.24 → 20.87 ms(−6.1 %);3-D 8M:s0 1,734 → 4.6 µs,周期 45.93 → 44.00 ms(−4.2 %),但现在 s1 偶尔等(p50 118 µs、平均 591 µs):新切点下 s1 的 n_B 少 1.0 %,是列粒度剩下的差,于是等的一方换了边。2-D 1M 较差链路暴露的步 10.2 → 4.9 %。两卡仍不同相(|Δ'| / T_B 中位数 narrow 0.82–1.00 → 0.70–0.71,8M 0.91–0.95 → 0.90–0.91),所以平衡后周期仍由慢的一侧加上相位差决定。
4. **集群算例(只计算)。** 旧规则在 2-D 4M–128M 上 K = 8 的偏差 0.20–1.95 %,新规则 0.09–0.67 %;3-D stretched 32M 2.44 → 0.55 %,stretched 64M 与 cube 401³ 不变(1.43 %、3.74 %:一列分别占一个 slab 的 2.0 % 与 8.0 %,切点已经在最近的边界上)。旧 ledger 的 64M K = 8"间隙 + 空闲"(2-D 3.8 %,3-D 3.2 %)里,切点最多占 2-D 的约 0.5 个百分点;3-D 的 1.4 个百分点来自列粒度,这次的修正去不掉。
5. **phase C:2-D 的约 0.21 ms 来自三个 band kernel 的延迟底线。** correction / density / force 的 boundary kernel 每步各 61.4 / 69.5 / 72.3 µs,合计 203 µs,在 2-D 10k(band 1,845 个粒子、39 个工作组)与 2-D 1M(15,345 个、309 个工作组)上完全一样,与 band 的大小无关(每粒子 4.0–39 ns,interior 0.5–0.7 ns)。启动 + 屏障 + 按池容量派发的三个小 kernel(expand、install、departed)合计约 9 µs,不是来源;内侧 ghost 列的自算(V6_GHOST_LAYERS = 2)在 2-D 不增加时间(含 ghost 列的 correction / density 与只算 own 列的 force 线程数相同、耗时相近)。同样的底线也让 2-D 10k 的 phase B 不随粒子数减半(interior kernel 75–98 µs)。3-D 的 band sweep 是吞吐受限的,每粒子 3.1–4.0 ns,是 interior 的 1.26–1.41 倍;3-D 8M 的 phase C 6.0 ms 里 band kernel 5.8 ms、密度拷贝 0.2 ms。
6. **C → A 间隙就是 phase A 等 frame_done(n − 1) 的那一个 semaphore。** phase A 开头只等本卡 main 时间线 ≥ frame_done(n − 1),它由本卡 C(n − 1) 在同一 compute 队列上 signal。去掉这个等待(`V6_PHASE_A_NO_WAIT=1`)后间隙 p50 从 36–37 µs 降到 5.6 µs(K = 1 的水平),fps +4.2 ± 2.8 %(2-D 10k)、+2.0 ± 1.1 %(2-D 1M),3 对交替。单步门与 A/B 门都通过,但它们逐帧等待(depth 1),碰不到这个等待;depth 2 下的证据是 8 次 =1 的运行共 24,000 步 drift 0、帧戳错误 0、溢出 0。默认没有改。
7. **对 E7:** 算例矩阵不用改,但以前的集群数与 E7 在 2-D 4M / 8M 与 3-D stretched 32M 的 K = 8 上不可直接比(切点变了);phase C 在 freeze 前没有低成本的缩短办法(大头是 band kernel 本身,要改 kernel);`V6_PHASE_A_NO_WAIT=1` 是现成的、实测有效、门已通过的开关,建议 E7 成对测(集群 64M K = 8 的 ledger 里 c → a 有 0.25 / 1.90 ms)。见最后一节。

### 2. 修改

`experiment/v6/utils/partition_v6.py`(提交 `b0cd868`):

- `nearest_cut(cumulative, target)`:`searchsorted(side="left")` 给出第一个前缀 ≥ 目标的列 k,候选切点是 k(左 slab 到 k − 1 为止,前缀 cumulative[k − 1] < 目标)和 k + 1(左 slab 包含第 k 列,前缀 cumulative[k] ≥ 目标),取前缀离目标更近的那个。**等距时取 k**,即旧算法的选择:已经精确或本来就等距的算例切点不动。注释里写明了这条规则与 E29 的例子(`b0cd868` 的注释与提交说明写成了"均匀格点的目标都正好在列边界上",不对,`54659b0` 改正了注释)。

- `compute_k_split`(旧的 2 卡入口)还有一个调用者:`legacy_dual_gpu_partition`,它只作 `_test_partition_chain.py` 的黄金参照。它的切点规则一起改成 `nearest_cut`,所以 N = 2 的黄金等价仍然成立;`legacy_dual_gpu_partition` 的注释里注明了这次改动。

## (c) C → A 间隙(只诊断)

**phase A 开头等什么。** per-direction 方案(`sync_scheme_v6.PerDirectionTimelineScheme`,生产默认)里,每帧 compute 队列的 A、B、C 在一次 `vkQueueSubmit2` 里提交(`submit_frame_compute_fast`):A 等本卡 main 时间线 ≥ frame_done(n − 1) = 3n、signal phase_a_done(n) = 3n + 1;B 不等也不 signal;C 等 upload_done(n) = 3n + 2(K = 1 时等 phase_a_done(n))、signal frame_done(n) = 3n + 3。所以 A 等的只有一个值,由本卡 C(n − 1) 在同一队列上 signal;K = 1 与 K = 2 等的是同一个东西。区别在于 K = 2 时 main 时间线还由 transfer 队列 signal(最后一个方向的 upload 给 upload_done),C(n − 1) 自己等的是这个跨队列的 signal,主机上的 worker 也在等它(dest_upload_guard)。phase A 的命令缓冲以一个 compute → compute 屏障开头,`a_start` 是它前面的 BOTTOM_OF_PIPE 时间戳,两者都排在此前提交的全部命令之后,所以去掉 semaphore 等待后 A(n) 仍在 C(n − 1) 之后执行(这是 `simulator_v6.py` 里 V3.6 注释的理由)。

## 对 E7 的影响

- **算例矩阵不用改。** 切点修正之后 K = 2 的 slab 在列粒度内是平衡的,E29 建议的点(2-D 每卡 n_B ≈ 32k / 130k / 0.5M / 2M / 8M,3-D 0.7M / 4.7M 加一个窄 slab)照用。要注意三件事:(1) E7 与以前的集群结果在 2-D 4M / 8M 与 3-D stretched 32M 的 K = 8 上不可直接比(旧规则在那里差 1.2–2.4 %);(2) 3-D cube 401³ 在 K = 8 时一列是一个 slab 的 8 %,切点修正帮不上,要么用 weights 微调,要么在报告里把它当成负载不平衡的点;(3) 平衡之后谁在 B → C 等,取决于剩下的不到 1 % 的差和两卡的相位(3-D 8M 换成了 s1 等),看每个 sim 的 B → C 等待,而不是只看一条链路。
- **phase C 在 freeze 前不能低成本缩短。** 2-D 的 0.21 ms 是三个 band kernel 的延迟底线,3-D 是 band 每粒子多 27–41 %,都要改 kernel;能拿到的上限:2-D 1M 约 +16 % fps,3-D 8M 约 3 %。密度拷贝(1–2 %)也要改代码。这些留到 freeze 之后。
- **`V6_PHASE_A_NO_WAIT=1` 值得在 E7 里成对测。** 本机 2-D 小 N +2–4 %,门已通过;集群 64M K = 8 的 ledger 里 c → a 有 0.25 ms(2-D)与 1.90 ms(3-D),这个开关可能拿回其中一部分(V3.6 的注释里 64M K = 8 的 c → a 有 0–0.5 ms)。是否改成默认由你定。
