## 结论

1. **传输链本身符合模型。** 去掉"等接收方"的两段之后,传输链 t_chain = τ0 + B_host / β:**τ0 = 122.3 µs、β = 3.76 GB/s**,18 条链路(B_host 39 KiB – 11.8 MiB)相对残差 rms 4.9 %、最大 9.6 %。分三跳:readback 48.3 µs + DMA 字节 / 28.3 GB/s,host 48.4 µs + 主机字节 / 7.26 GB/s,upload 21.3 µs + DMA 字节 / 16.0 GB/s。
2. **按任务定义的 t_tr 含两卡的相位差,不能拿来拟合。** t_tr 从发送方 ghost_send 结束算起;worker 拷贝前要等接收方自己的 readback_done(n)(时间线守卫),所以接收方落后时 t_tr ≈ 相位差:2-D 16M 一条链路 t_tr p50 12.7 ms(T_B 12.8 ms),另一条 0.5 ms。用 t_tr 拟合得 τ0 = 407 µs、β = 0.79 GB/s,相对残差 rms 214 %。逐步较差链路的 r = t_tr / T_B 的 p50 是 0.45–1.00,主要由相位差决定;所以下面另给 r_chain = t_chain / T_B 与 r' = (upload 结束 − 接收方 B 开始) / T_B(> 1 即暴露)。
3. **c_B 与 r_pred。** c_B(K = 1 的 T_B 对 N,过原点)2-D 1.611 ns / 粒子、3-D 8.133 ns / 粒子。2-D 在 N ≥ 1M 时各算例的 T_B / N 是 1.61–1.66 ns,K = 2 的 T_B 与 c_B · n_B 差 −0.5 … +8.7 %;3-D −1.6 … +9.7 %。**N ≥ 1M 的 6 个算例 r_pred 与实测 r_chain p50 差 −7.3 … +12.1 %**(2-D 1M / 4M / 16M:0.259 对 0.231、0.090 对 0.089、0.036 对 0.039;3-D 1M / narrow / 8M:0.206 对 0.193、0.257 对 0.231、0.093 对 0.096),闭式近似与 r_pred 差 −0.6 … −5.7 %。**小 N 失效**:phase B 被派发开销主导(2-D 10k 的 K = 1 T_B 252 µs,K = 2 每卡 247–249 µs,不随粒子数减半),c_B · n_B 只有 8–10 µs,r_pred = 16 对实测 0.59;改用该算例自己 K = 1 的 c_B 也只到 1.5 对 0.59。
4. **η 为什么在 r < 1 时就掉。** r_chain 的 p50 全部 < 1(0.04–0.59)、p95 ≤ 1.03:传输链本身基本藏得住。η 的损失是 K = 2 每步比"K = 1 的一半"多出来的时间(见"每步时间构成"):
   - **2-D:多出来的是藏不进 phase B 的固定工作。** phase C 每步多 153–286 µs(K = 2 的 C 是 band、install、展开、departed 等一串小派发:10k–1M 是 211–233 µs,K = 1 只有 4–39 µs)、phase A 多 21–117 µs(ghost_send)、主循环门控多 35–43 µs(C 结束 → 下一步 A 开始:K = 2 37–46 µs,K = 1 5–6 µs);小 N 时 phase B 也不减半(多 56–126 µs)。10k 的 K = 2 一步约 560 µs(中位数),是 K = 1 一半的 3.9 倍,η = 24 %;1M 多约 340 µs,η = 71 %;4M、16M 多出的时间相对 T_B 已小,η = 93–95 %。
   - **3-D:phase C 很重。** 每步 2.9 ms(1M,w = 15–16)、5.8–5.9 ms(narrow,w = 12–14)、6.3–6.4 ms(8M,w = 27–29),K = 1 只有 0.06–0.36 ms;C / B = 0.49–0.50、0.37–0.44、0.16–0.17。B 比 K = 1 的一半短 0.5–6.0 ms(band 粒子挪到了 C),相抵之后仍多出。
   - **slab 负载不均让快的一边每步干等。** weights 1,1 分出的两个 slab 在 3-D narrow 差 21 %(n_B 1.48M 对 1.79M)、3-D 8M 差 7.5 %、3-D 1M 6.6 %;较快的 s0 每步在 B 与 C 之间等 s1 的数据(narrow 中位 3.06 ms、8M 1.73 ms)。这在 r' 上是"暴露"(98.7 % / 69.7 % 的步),但不是传输(r_chain p95 0.26 / 0.12)。2-D 除 10k(21 %)外 n_B 差 0.5–6 %。
   - **两卡不同相。** 慢的一边决定周期,快的一边一直往前跑到被数据卡住,所以 |Δ'| 中位数在 2-D 16M、3-D narrow、3-D 8M 达到 0.81–0.99 个 T_B,3-D 1M 0.55,2-D 62k–4M 0.22–0.37,2-D 10k 与 1M ≤ 0.04。旧的 r 假设两卡同时进入 phase B,把这一项混进了传输。2-D 16M 的中位数上没有等待,但 38.6 % 的步在等(平均每步 455 µs);按 fps 算的平均周期 15.04 ms 比中位数 14.39–14.53 ms 长的部分就是它。
5. **host 步(补完 E24)。** 2-D 1M 每条链路:memcpy 45 µs(p95 89 µs,7.3 GB/s)、帧戳检查 1.1–1.3 µs、signal 13.5–13.8 µs、等接收方上一步 upload 5 µs、等接收方 readback_done 26–36 µs(p95 640–660 µs);"等发送方 readback"1.08–1.12 ms 是 worker 提前取到帧号、在等 GPU,不在关键路径上。主机拷贝 7.0–7.35 GB/s(2-D 1M、16M、3-D 8M)。落后接收方那条链路的"等接收方 readback_done"就是相位差(16M 12.2 ms、3-D 8M 35.0 ms)。

## 记录字段(E7 沿用)

开关:`experiment/v6/_run_v6_chain_bench.py --step-trace DIR`(默认关;关时录制与提交的 GPU 命令和以前完全相同),`--step-trace-detail phases|full`(默认 phases:各 phase 的开始与最后一个 tick、两个 ghost_send 的结束、全部传输 tick;full 另加 phase 内每个 kernel 的 tick),`--step-trace-calibrate-ms`(默认 500)。实现:`experiment/v6/utils/phase_trace_v6.py` 的 `StepTracer` / `StepTraceTimer`;共享文件只改了 `simulator_v6.py`(按帧奇偶各录一份 phase A/B 与传输命令,只在 trace 打开时)和 `transport_v6.py`(worker 的主机时钟可替换、多一个帧戳检查时间点、每步拷贝字节)。每次运行一个目录,四个文件;时间一律是**主机时钟上的 ns**(整数)。

**时间基准。** GPU 时间戳经 `VK_KHR_calibrated_timestamps` 映射到主机时钟:一个辅助线程每 500 ms 采一次(每次连采 3 对、取驱动 maxDeviation 最小的一对;驱动调用不占主循环),开头、warmup 边界(流水线排空时)和结尾各采 5 / 3 / 5 次(每次 8 对)。每台设备的映射 = 稳健最小二乘直线(3σ 迭代剔除)+ 直线残差的 9 点滑动中位数(按设备时间线性插值);同一设备的 compute 与 transfer 两个计时池共用这一映射。需要后一项是因为两种钟的频率比在几分钟里会漂几个 ppm:3-D 8M(140 s)单用直线时残差是一条 ±16 µs 的抛物线(rms 9.7 / 7.5 µs),加上后 rms 2.1 / 1.3 µs。驱动报的 maxDeviation 最小约 12 µs:每一对标定样本的两个读数之间就有这么宽的窗口,所以 GPU 与主机之间的**绝对**对齐只能保证到这个量级;拟合残差(下面检查里的容差)衡量的是映射本身的一致性。主机时钟 = worker 时间点用的钟:Windows 是 QPC(`time.perf_counter_ns`,本机 QPC 10 MHz,与 perf_counter_ns 一致到 100 ns 一格);Linux 是 CLOCK_MONOTONIC(`perf_counter_ns`),驱动只给 CLOCK_MONOTONIC_RAW 时 tracer 与 worker 都改用 `time.clock_gettime_ns(CLOCK_MONOTONIC_RAW)`——**Linux 两条路径都没测**,E30 的 S1 会报集群上的时间域。

**时间戳为什么每步都在。** 每个按帧的标签在计时池里有两个槽(偶数帧一块、奇数帧一块),第 n 步的 phase A 第一件事是复位本奇偶的块(compute 池直接复位;transfer 池由 phase A 在 compute 队列上复位——transfer 队列不能复位查询池)。第 n 步的块要到第 n + 2 步的 phase A 才会被复位,而 depth-2 主循环在读完第 n 步之后才提交第 n + 2 步;第 n − 2 步的 readback / upload 也一定在第 n 步的 phase A 之前完成(phase A(n) 等 frame_done(n − 1),后者经 upload_done → worker → 本卡 readback_done(n − 1) 排在本卡 readback(n − 1) 之后)。所以只能用 depth ≤ 2(bench 会拒绝 depth 3)。

### 派生量(`experiment/v6/analysis/step_trace_model.py`)

- t_tr = `upload_end − send_end`,无重叠地拆成 11 段:readback 启动(`send_end → readback_start`)、readback DMA、屏障、readback 结束 → worker 看到(`readback_end → worker_source_wait`)、等接收方 readback_done、等接收方上一步 upload、帧戳检查、memcpy、signal、signal → upload 开始、upload DMA。按任务的五段合并:readback = 前三段;readback 结束 → worker 看到;host 段 = 中间四段(两段等待 + 帧戳 + memcpy);拷贝结束 → upload 开始 = signal + signal → upload 开始;upload = upload DMA。
- host 步(worker,补完 E24):等发送方 readback(`dequeue → source_wait`,与 GPU 段重叠,不在 t_tr 的关键路径上)、等接收方 readback_done、等接收方上一步 upload、帧戳检查、memcpy、signal。
- T_B = 接收方 `b_end − b_start`;r = t_tr / T_B,逐步取较差的链路。
- 相位差 Δ' = 接收方 `b_start` − 发送方 `send_end`。
- 暴露时间 = max(0, `upload_end` − 接收方 `b_end`);C 前总等待 = 接收方 `c_start − b_end`。
- 主循环门控 = 每 sim 的 `a_start(n) − c_end(n − 1)`。

## 第二段:本地扫描与模型

**做法。** 9 个算例:2-D 10k(`logs/two_hop_experiment/cases/cavity_2d_10k`,每 slab 12 / 14 列)、62k、250k(用 1M 的生成器与参数新生成,见下)、1M(`lid_driven_cavity_2d_gen`)、4M、16M;3-D 1M、narrow(每 slab 12 / 14 列)、8M。每个算例依次:K = 1 在 GPU 0 与 GPU 1 上同时各一个进程、K = 2(GPU 0,1),都不开仪器(η 用这两次的 fps);再同样两次都开仪器(分解;K = 1 的 T_B 给 c_B)。各一次,不做多次试验。η = fps_K2 / (2 · mean(fps_K1,GPU 0, fps_K1,GPU 1))。

**定义的补充。** 除了任务定义的 r = t_tr / T_B,还给了两个比值,原因见结论 2:t_chain = t_tr − 等接收方 readback_done(n) − 等接收方上一步 upload(传输链本身),r_chain = t_chain / T_B;r' = (upload 结束 − 接收方 B 开始) / T_B,大于 1 即这一步暴露。三个比值都逐步取较差的链路。τ0、β 用 t_chain 拟合,r_pred 用这组常数;按任务定义用 t_tr 拟合的结果也列出。c_B 是每维一条过原点的直线(K = 1 的 T_B 对 N);"本算例 c_B"是该算例自己 K = 1 的 T_B / N,只作对照,没有拟合。

## 对 E7 的建议

**必须记的字段。** 上面的规格整套照用(`--step-trace DIR`,默认的 `phases` 细度):每步每 sim 的 phase A/B/C 起止与两个 ghost_send 的结束;每步每条有向链路的 readback / upload DMA 起止、worker 的 7 个时间点、主机拷贝字节与 DMA 字节;`run_meta.json` 里的 w、band、n_B(warmup 边界从 voxel 计数读)、映射参数与残差、驱动 maxDeviation。只记 t_tr 不够:要把落后的接收方造成的等待(`worker_dest_guard − worker_source_wait`)与传输链本身分开,并且要有接收方的 b_start / b_end 才能算暴露(r')。K = 8 的链上每条链路都有自己的相位差,逐条链路记录(工具已经这样做)。

**η 与分解分开跑。** 仪器在 1M 量级的步长上要 1.1–1.5 %(本机),所以 η 用不开仪器的运行,分解与 r 用开仪器的运行;每个算例两次(或更多)K = 2、K = 1 参照各开 / 关一次。

**时钟。** 集群是 Linux:tracer 选 CLOCK_MONOTONIC(否则 CLOCK_MONOTONIC_RAW,同时把 worker 的主机钟换掉);这两条路径都没测,先看 E30 S1 报的时间域,并在第一批运行里检查 `run_meta.json` 的映射残差与驱动 maxDeviation。运行长于几十秒时直线映射不够(本机 140 s 有 ±16 µs 的弯曲),已经用滑动中位数修正;集群上要确认同样有效。

**算例矩阵要覆盖两个区。** 本机看到两个区。(一)每步固定成本与传输区:2-D 每卡 n_B ≲ 1M(T_B ≲ 0.9 ms),K = 2 每步多出的固定工作约 0.3 ms(phase C ≈ 0.21 ms、ghost_send、门控)与传输链 t_chain ≈ 0.14–0.2 ms 都与 T_B 同量级,η 24–71 %;(二)计算区:2-D n_B ≳ 4M、3-D 宽 slab,r_chain ≤ 0.1,η 由 phase C / A 的附加工作、slab 负载差与相位差决定。集群上两区都要有点:2-D 每卡 n_B ≈ 62k / 250k / 1M / 4M / 16M,3-D 每卡 1M / 4M / 8M,其中留一个窄 slab(w − b ≈ 9–11,本机 r_chain 0.23);K = 2、4、8。K ≥ 3 的中间 slab 有两条 seam:phase C 的 band 与 ghost_send 加倍,n_B 两侧都扣 band,两条入站链路各有相位差,要单独看。用 r_chain(而不是 t_tr / T_B)和 r' 判断传输是否藏住,用每步时间构成(A、B、B→C、C、门控)解释 η。

**同时记录的协变量。** 每卡的 SM 时钟与功率(集群脚本已有的 nvidia-smi 采样)、每 slab 的 own 粒子数与列数(负载是否平衡决定相位差往哪边漂)。
