## 第 2 部分:权重校准(`--weights auto` / `--weights-file`,原 E28)

### 1. 实现

模块 `experiment/v6/weight_calibration.py`(放在 `utils/` 外:它不是物理,validation runner 按 `experiment/v6/utils/*.py` 算的物理哈希不受它影响),接进 `experiment/v6/_run_v6_chain_bench.py`。

- **pilot。** 用等权重(或 `--calibrate-from` 给的权重)建链,bootstrap + defrag(与每次运行相同),跑 W 步 warmup(`--calibrate-warmup`,默认 200)再测 M 步(`--calibrate-steps`,默认 300),depth 取 min(`--depth`, 2)。每个 sim 挂一个只记 phase 起止的 `StepTraceTimer`(compute 池,`PHASE_TICKS`:a_start、A 的三个结束点、b_start、B 的两个结束点、c_start、c_force_end;不挂 transfer 计时器,不做时钟标定,不需要 calibrated-timestamps 扩展),每帧在它的 frame_done 之后读一次奇偶块(depth ≤ 2 时这块要到 A(n + 2) 才会被复位,而 A(n + 2) 在读完之后才提交)。T_X = 该 phase 最后一个结束 tick − 开始 tick,按整数相减。
- **忙时。** busy = T_A + T_B + T_C:a_start 在 C(n − 1) 之后,c_start 在 upload_done 的等待之后,所以不含任何等待;每台设备取 M 帧的中位数。一张卡上有几个 sim 时(device map 0,0,1),卡忙的时间是这几个 sim 的全部 phase 区间的并集(同一个 GPU 时钟),按帧平均;并集若超过实际经过的时间,说明时间戳不在同一时钟上,改用最大的那个 sim 的中位数(本次没有发生)。
- **ω 与切点。** ω_k = 第 k 个 slab 的流体粒子数 ÷ 它所在设备的忙时;流体数来自算例初始状态的流体直方图(`_bin_fluid_counts`,也就是切点规则切的那个),所以墙算进时间、不算进分子,带墙的端部 slab 会分到较少的流体。切点用 `chain_cuts_from_counts`(E31 规则)重算;变了就用 ω 再做一轮 pilot(最多 `--calibrate-rounds` 轮,默认 2),最后一轮的 ω 是结果。每轮 pilot 是一条独立的链(新的 context、sim、时间线),跑完拆掉再建下一条:同一条链不能跑两次(帧号从 0 重来,时间线的值不回退)。计时的链在全部 pilot 之后才建,所以 pilot 时间不在计时窗口里。pilot 的 drift、溢出、帧戳错误、远距迁移必须为 0,至少 90 % 的帧要有全部 phase tick,否则中止。
- **记录。** 每轮一组 `[calibrate]` 行(权重、切点、own 列、流体数、全部粒子数,每个 sim 的忙时 p50 / p95 与 A / B / C 的 p50,每台设备的忙时与算法,ω,下一组切点,pilot fps 与用时,不变量),然后 `[calibrate] final` 与分隔行 `[calibrate] done`;pilot 不打印 `STEADY`、`TOTAL`、`final:` 行,取第一个匹配的解析器不受影响。计时运行打印 `[chain_v6] weights source=auto|file|given cuts=[…] file=… sha256=…`,`--step-trace` 的 `run_meta.json` 里有 `weights_source`、`weights_file`、`weights_file_sha256` 和整份 `weight_calibration`。
- **`--weights-file`。** 与 `--weights auto` 一起时保存整份记录:算例路径与 case.yaml 的 sha256、粒子数、列数、流体直方图的 sha256、K、device map、节点名、各卡的名字与 UUID、commit 与 v6 的未提交文件、`V6_*` / `VK_*` 环境、band 宽度、pilot 设置、每一轮、全精度的最终权重与切点。单独用时复用:K 与 device map 不符、流体直方图不符、或由保存的权重重算的切点与保存的不同,都报错;节点或 case.yaml 不同只警告。`--calibrate-only` 存完就退出(E7 每个算例、K、节点校准一次)。
- **代价。** 每轮 pilot:2-D 1M 1.4 s,3-D narrow 12 s,3-D 8M 26 s,2-D 4M K = 3 5–6 s。

**单元测试** `experiment/v6/_test_weight_calibration.py`(只用 CPU,37 项):phase 区间(含不同配置下 phase 的最后一个 tick 与不完整帧)、区间并集、单 sim / 共享卡顺序执行 / 共享卡交错执行 / 时间戳不同时钟四种忙时、device map 0,0,1 在均匀直方图上给 ω = (1, 1, 2) 与 1/4、1/4、1/2 的流体份额、有固定开销时第一轮欠修正而第二轮更近、对称时切点不动、权重文件的往返与三种拒绝。

### 3. 诊断:3-D 8M 的校准为什么在计时运行里输了

- **不是仪器。** 怀疑过 phase 时间戳本身拖慢 GPU 0(E29 的单次数据里 3-D 8M 的 K = 1 在 GPU 0 上开仪器慢 3.3 %、GPU 1 只慢 0.3 %;本次带 trace 的 3-D 8M K = 2 两次运行里 GPU 0 每粒子都慢 6–9 %)。对照(`tracecost`:3-D 8M K = 1 两卡同时跑,关 / 开 step trace 交替各 2 次,1500 步 / warmup 500):GPU 0 关 11.427 / 11.426、开 11.381 / 11.410 fps,GPU 1 关 12.082 / 12.080、开 12.044 / 12.072 fps,开仪器只慢 0.3 % / 0.2 %。

## 第 3 部分:E7 算例的几何对齐(只用 CPU)

### 1. 为什么旧算例切不平

两个旧生成器(`_demo_cavity_case.py`、`_demo_cavity_case_3d.py`)都是节点格点:[−0.5, 0.5] 上 2 half + 1 个粒子(两端都有粒子),每个方向是奇数个,有效宽度 1 + dx;voxel 网格由加载器从 frame.obj 的包围盒推出(origin = 包围盒最小值 − h/2,列宽 h = (h/dx) dx),第一个流体格点列离 origin 14.1 dx(2-D)/ 6.6 dx(3-D border 4),所以第一个流体 voxel 列只部分填满,最后一列填几格取决于尺寸。奇数个格点列既填不满整列,也不能平分。

### 2. 做法:格心格点 + 与之对齐的 frame

新生成器 `utils/geometry/_demo_cavity_case_aligned.py`(只依赖 numpy):

- **格心格点。** 流体是 n_x × n(× n)个粒子,放在空腔 dx 网格的格心:x ∈ [−n_x dx / 2, n_x dx / 2],y(、z)∈ [−0.5, 0.5],dx = 1 / n;墙与盖是外面再 `border` 层格心(盖在流体正上方、宽度与流体相同,墙是其余部分,与旧生成器同样的 U 形 / 壳形)。h/dx、c0、CFL、ξ 0.001、ε² 0.0025 h²、盖速 1 m/s、材料库都与旧生成器相同。
- **frame 的取法(即 grid origin)。** frame 的 x 半宽取 n_x dx / 2 + (W − 1/2) h,W = max(1, ⌈(border − 1/2) / (h/dx) + 1/2⌉) 是每侧的墙列数:加载器由此得到的 origin 正好在左边流体边界外 W 列处,列边界与两侧流体边界重合。n_x 是 h/dx 的倍数时流体正好占 n_x / (h/dx) 个整列,这个数再是 8 的倍数,K = 2 / 4 / 8 的等权重切点就都落在列边界上,每个 slab 的流体粒子数完全相同。y / z 方向同样取 W 列,盖与墙都在网格内。
- **物理不变。** voxel 网格只用来找邻居,列的位置不进入物理;格点换成格心只把空腔的有效尺寸从 1 + dx 变成正好 1(粒子代表的方块正好铺满 1 × 1),是 dx 量级的离散差别,不是参数变化。h 与 dx 以全精度写进 case.yaml(旧生成器写 `%.6f`,在 2,000 多列上会把 voxel 边界移动最多一列),位置写 9 位小数。
- **写之前先检查。** 生成器按加载器与 `partition_v6._bin_fluid_counts` 的方式(位置与 frame 先按文本解析成 float32,在 float32 里分箱)重算每列的流体数,要求整列、每列相等、第一流体列 = W、列数 = 流体列 + 2W,不满足就报错。`--yaml-only` 只写 case.yaml 与 generate.txt(仓库只收这两个,.obj 被 git 忽略),`--objs-only` 按 generate.txt 重建粒子文件。
- **用真实加载器验证。** 生成了 3 个算例的粒子文件(2-D n1000、3-D n104_b9、窄 slab n200_x96),`cut_balance --validate` 用 `case_loader_v6` 加载、用 `compute_chain_partition` 切:加载器的逐列流体数与全部粒子数与生成器的模拟逐列相同;每个 slab 的流体 2-D n1000 在 K = 2 / 4 / 8 是 500,000 / 250,000 / 125,000,3-D n104_b9 在 K = 2 是 562,432,窄 slab 是 1,920,000,偏差 0.000 %。旧格点的模拟照旧与加载器一致(本机 Blender 导出的 4M 除外,与 E31 相同)。

## E7 脚本要改的地方

1. **提交。** E7 要跑 E32 之后的提交(no-wait 默认、E31 切点、`--weights auto` / `--weights-file`、对齐算例)。`probe36` / `probe37` 写死了 `COMMIT=63c5e43`(probe37 不一致就退出),E30 的 `deploy_v6.sh` 按 SHA 部署,都要换成 E32 的提交。
2. **no-wait 默认。** 脚本不用 export 任何东西;要做 =0 的对照臂就 `export V6_PHASE_A_NO_WAIT=0`。probe34–38 的表头现在打印代码默认与实际取值,E30 的 `run_chain_v6.py` 打印 `simulator_v6._PHASE_A_NO_WAIT`。钉 `LEGACY_DEFAULTS` 的 seam_audit 工具照旧跑 0。
3. **权重。** 每个(算例、K、节点)在试验之前紧挨着校准一次:`--weights auto --device-map D --weights-file $LOG/weights/<算例>_k<K>.json --calibrate-only`(超时留出最多两轮 pilot:每轮建链 + bootstrap + 500 步,64M 级算例的建链是分钟级);K > 1 的每次试验用 `--weights-file <同一文件>` 代替 `--weights`;K = 1 参照照旧 `--weights 1`。文件按节点分开存(换节点只警告,不会拦),拷进 `$LOG`。结果行加 `weights`、`cuts` 与权重来源(从 `[chain_v6] weights source=` 一行读)。计时试验不要用进程内的 `--weights auto`:日志会多出 pilot 的分区行与 bootstrap 行,`parse_run_v6.py` 取第一个匹配会读到 pilot 的,`run_chain_v6.py` 按 `id()` 记的 clamp 计数也会混进 pilot 的 sim;非用不可时,解析器只读 `[calibrate] done` 之后的部分。第 2 部分第 3 节的教训:校准只代表 pilot 那一刻,所以等权重的对照臂要保留,并用同时跑的 K = 1 参照在各卡上的 fps 之比检查卡与卡的差别在试验期间是否稳定。
4. **算例路径。** 换成 `cases/aligned/` 下的新算例(第 3 部分的表):
   - 2-D strong 4M–128M → `cavity2d_n2000`、`_n2840`、`_n4000`、`_n5640`、`_n8000`、`_n11320`(K = 1 参照装不下,或改用 `_n9000`);K 扫描 32M / 64M → `cavity2d_n5640` / `_n8000`。

   - 3-D weak 族(每卡 4M / 8M)→ `cavity3d_n160`、`cavity3d_n200` 与 `_k2` / `_k4` / `_k8`(k8 = strong 矩阵的 stretched 32M / 64M);立方体 → `cavity3d_n416`。
   - E29 的逐卡点 → 2-D `cavity2d_n240` … `_n8000`(按 K 选,见表的"用途"一栏),3-D `cavity3d_n104_b9`、`cavity3d_n200_b9`、窄 slab `cavity3d_n200_x96`。
