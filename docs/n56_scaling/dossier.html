The transport layer is fully hidden at ≥8M particles per GPU; the residual 4–9% at heavy load is per-GPU speed spread (SM clocks 2662–2784 MHz across cards, phase B 12.1–12.9 ms for equal particle counts) plus fixed per-frame costs, not communication. Below ~4M per GPU the 8-way chain is latency-bound and run-to-run bimodal. Every optimization on the CPU submission path was implemented and validated but moved the idle around rather than removing it.

Efficiency definition (standardized 2026-09-15)

GPU clocks cannot be locked (no root; nvidia-smi -lgc unavailable), and cards on one node differ by 2–4% in single-GPU throughput. Every reported efficiency therefore follows this protocol:

  • Reference = the K=1 throughput of every GPU that takes part in the K-GPU run, measured on all of them simultaneously (same power/thermal state), same case, same window. η_strong(N,K) = fps_K(N) / (K · meani fps_1(N; GPU i)); η_weak(K) = fps_K(K·n) / meani<K fps_1(n; GPU i).
  • Window: chain bench, 3000 steps, steady = last 2000 (identical physical window for reference and K run; the flow is still developing in this window — see gaps).
  • Error bar = std over 3 alternating trials (trial t's K run over trial t's reference). Per-GPU reference spread reported separately.
  • η_min = fps_K / (K · mini fps_1): an equal-slab chain cannot beat its slowest card, so η_mean − η_min is the hardware-spread term; the rest is decomposition + transport.
  • Telemetry (nvidia-smi every 5 s: SM clock, power, temperature per GPU) recorded for every job as a covariate.
  • When K=1 does not fit one 32 GB card (128M, 256M total), the reference is K=2 pairs on all GPUs with factor K/2.
Protocol scripts: docs/n56_scaling/scripts/probe34_curve.sbatch (strong), probe35_weak.sbatch (weak), analysis plot_curve34.py / plot_weak35.py. Earlier single-trial numbers (probe13/14, 2026-09-15 morning) predate this protocol and used one reference GPU.

Correctness evidence for the changes

  • Chain bench seam checks (4M K=2 and K=4, N56): particle total exactly conserved, drift 0, seam overshoot < 0.02 dx, 0 duplicates, transport stamp errors 0 (every ghost packet carries a frame stamp checked on receipt) — for cascade, band, fast, no-wait, ready.
  • Equivalence battery (_run_v5_equivalence.py, local 2×5090, configs 1,1,2,2, 2000 steps, cascade on): all aggregate metrics within the K=1 run-to-run envelope.
  • Per-particle verifier (experiment/v5/_verify_cascade_force.py, new): 4 runs (A×2, B×2), KD-tree particle matching, per-field max/p99.9 diffs, acceleration diff by voxel-column distance to the nearest seam vs the run-to-run noise floor; PASS if worst column ratio < 3 and the band invariant (voxel-list reach == coordinate membership for bands 2/3/4) holds. Results: legacy vs cascade 1M K=2 300 steps ratio 0.53–1.06; K=4 0.72–1.37; 4M K=2 0.70–1.37; 2000 steps 0.76–1.40; cascade+band vs legacy 0.5–1.4; fast, no-wait, ready each vs its predecessor 1.2–1.4; on-cluster global vs ready 4M K=4: 1.02 (300 steps), 1.24 (2000 steps).
  • Soaks: every 64M K=8 soak (0.07 h, 16–17k frames) drift 0; longest N56 soaks are 0.07 h — no multi-hour Linux soak yet.
  • Bit-exactness is impossible on this solver (atomicAdd slot ordering → neighbour sum order), so "indistinguishable from run-to-run noise" is the standard.

Known gaps & open questions for the audit

  • Light-load bimodality is unexplained. At ≤4M per GPU identical configurations give 2× different fps (2M/GPU K=2: 119/245/179; 4M K=4 seam bench: 138/142/177/198/199/287). Hypothesis: the chain locks into an exposed-transport phase pattern per run; candidate diagnostics: per-link upload-to-C gap traces over time, periodic resync, ready scheduler at light load ×N, GPU clock state at light load. Not tested.
  • Per-GPU speed spread is now the largest heavy-load term (phase B 12.1 vs 12.9 ms for equal counts; η_mean − η_min ≈ 1–2%). No weight rebalancing by measured per-GPU speed was attempted (static per-card weights or dynamic load balancing, V3.1 in the roadmap).
  • Flow-development bias. All standardized numbers come from steps 1000–3000 of a cavity starting from rest. The 12-hour local soak showed fps falling 120 → 109 as the flow develops (migration grows). Steady-state efficiency at developed flow is not measured on N56; the 0.07 h soaks reach ~17k frames only.
  • Reference substitutes. 128M and 256M references use K=2 pairs (factor K/2), so η at 16M and 32M per GPU includes one decomposition level in the reference. Single-GPU ceiling on N56 (largest N that fits a 32 GB 5090) not measured; local rig ceiling ≈ 90M.
  • Mixed nodes. Sizes were measured on two nodes with different power caps (575 W vs 600 W). Each η is intra-job/same-node, but absolute fps across sizes mixes nodes; only one node pair sampled — no cross-node variance study.
  • Only K=8 has a strong curve with error bars. K=2 and K=4 strong efficiencies exist only as single trials (probe13). No error-barred K sweep at fixed N.
  • Weak 2M family is missing K=3 and K=6 (cases have no geometry); weak curves are K = 1, 2, 4, 8 only. No weak point beyond 8 GPUs (single node).
  • 2-D only on the cluster. 3-D cases exist locally (8M single/dual validated) but nothing 3-D was run on N56. No physics validation (Ghia lid-driven cavity profiles) on the cluster runs; conservation/seam checks only.
  • Residual drift race caged, not closed. Memory records an earlier cluster-only, depth ≥ 2 random ±few-particle drift on the lab 3090 cluster (campaigns there ran depth 1). Every N56 run here used depth 2 and reported drift 0 (dozens of runs, up to 17k frames), but no dedicated re-test of that race on N56.
  • Scratch→primary density copy costs ≈0.3–0.4 ms/frame at 8M/GPU (≈2%) at every K including K=1; a compute-shader copy or descriptor ping-pong would remove it. Not attempted (affects absolute fps, not η).
  • Band kernels run at ≈2× the interior per-particle cost; cause not identified (ghost-slot cache misses? lane utilization of the 96-slot mapping?). Untested idea: 32-lane strided slot loop.
  • CPU tail spikes (submit max 12–35 ms per 1000 frames) remain with fast submit; source unknown (GC? worker GIL?). ≈1% effect.
  • Code is uncommitted and the server copy is synced by SFTP, not git; env-switch defaults differ from what the measurements used (cascade and band were ON in all curve jobs but default OFF in code). A decision on defaults and a commit are pending.
  • Wasted node time / cost accounting. Two 70-minute jobs were lost to a job-script bug (bare wait also waited on the telemetry sampler). Total whole-node hours on hp_5090 ≈ 15–18 across the three days (approximate; the accounting page was never read). The bringup_check.py --objs-only trap noted in memory is also unresolved.
  • Not measured here: K=8 at 3-D loads, inflow/outflow cases, multiple nodes (the design targets one node; no inter-node transport exists), NVLink/P2P (consumer GeForce has none — settled locally), weights sweeps on N56.
