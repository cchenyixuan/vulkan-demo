# 单卡基线:V0 参考求解器 vs V5 多卡求解器的单卡模式(2026-09-23 / 24)

## 结论(TL;DR)

- **多卡求解器 V5 在单卡模式下不慢于参考单卡求解器 V0:1M–32M 全程为 V0 的 100.1–102.0%**(两种在飞深度,每点 3 轮,标准差 ≤ 0.5%,120 次运行粒子数全部精确守恒)。
- 第一轮测量曾得到 95.6–97.4%(约 3.2% 的恒定代价)。逐 kernel 计时把差距定位在 density(+5%)和 force(+6–7%),对照实验证明 100% 来自 **邻居循环嵌套顺序与 V5 的 voxel 编码不匹配**:V5 为 slab 连续把编码改成 x 最慢(y 最快),三个邻居 kernel 却沿用 V0 的 `dx` 最内层循环。把最内层改成 `dy`(提交 `f9c660e`,只改求和顺序)后差距消失并反超 1–2%。
- 2 帧在飞对两种求解器的收益相同:1M +5%,2M +2.7%,4M +1.7%,≥8M ≤ 1%,32M +0.4%,对应每步约 100–165 µs 的 CPU 提交气泡。
- 单卡粒子吞吐 545–600 M 粒子·步/秒,随 N 缓升;两种求解器在同一尺寸下 SM 频率差 < 0.5%,全程 600 W 功耗墙,≤ 70 °C。

## 目的

为论文提供单 GPU 基线,并回答"多卡设计是否损害单卡性能":

- **V0** = 仓库里的参考单卡求解器(`utils/sph/` + `shaders/sph/`,`_run_viewer.py` 背后的代码路径)。它没有正式名称,也没有无头基准入口;本次新增 `_run_single_baseline_bench.py` 作为其基准入口。V0 原生循环是同步的:每步一次 `vkQueueSubmit` + fence 等待(1 帧在飞)。
- **V5 单卡模式** = 多卡求解器 `experiment/v5/SphSimulatorV5` 在无 peer 时的合并单步路径(predict → update_voxel → correction_all → density_all → force_all),无 ghost、无 timeline 信号量、无 worker 线程。

两者都以 1 帧在飞(各自的原生 submit+wait 循环)和 2 帧在飞(在同一条 `SIMULTANEOUS_USE` step 命令缓冲上用 fence 环提交,GPU 队列在两步之间不排空)各测一次。基准脚本不修改求解器。

## 方法

| 项 | 设置 |
|---|---|
| 硬件 | 单张无显示器的 RTX 5090(nvidia-smi index 1,PCI 03:00.0,按 UUID 固定),driver 576.88,600 W 功耗上限 |
| 算例 | 2-D 顶盖驱动方腔,1M–32M(`cases/lid_driven_cavity_2d_{gen,2m,4m,6m,8m,10m,14m,16m,32m}`),h/dx = 5,c0 = 100,γ = 7;1M 用与 2M–32M 同一生成器/同一物理参数的 `_gen` 算例;重调参过的 `lid_driven_cavity_2d`(c0 = 20,γ = 1.4)单列为 `1m_orig` |
| 度量 | fps = 计时窗口步数 / 墙钟时间;计时窗口起止都在 GPU 队列排空(所有 fence 等待完成)时取,因此对任意在飞深度都精确。无 GPU 时间戳,验证层关闭 |
| 窗口 | 预热 1000 步;计时 10000(1M)/ 6000(2M)/ 4000(4M)/ 3000(6M)/ 2000(≥8M)步,均为 1000 步 defrag 周期的整数倍,窗口内 defrag 次数一致 |
| 重复 | 每个点 3 次,四种配置在同一尺寸内背靠背交错运行、每轮轮换顺序,消除热态/流动发展的偏置;比值按"同一轮的 V5 / 同一轮的 V0"计算再取均值 ± 标准差 |
| 协变量 | nvidia-smi 1 Hz 采样 SM 频率 / 功耗 / 温度;全程 600 W 封顶,SM 2707–2810 MHz,最高 70 °C |
| 守恒 | 每次运行结束回读 alive 粒子数;两轮共 240 次运行 drift 全部为 0,无 overflow |

### 说明

1. 曲线上的每个点 V5 都 ≥ V0(100.1–102.0%),差异在 3 轮标准差量级或略高于它;可以在论文里写"多卡求解器在单卡上无退化(within ±2%)"。
2. **1M-orig(重调参算例,c0 = 20、γ = 1.4、单层墙)是唯一 V5 慢于 V0 的点(97.3%)**。它不在论文曲线上;V0 在这个算例上比在同粒子数的 `_gen` 算例上快 3%(538 vs 522),V5 则两者相同(524 vs 523),差异来自 V0 对该算例特有的粒子/墙布局更有利,仍待细查。
3. 2 帧在飞的收益:1M +4.6–5.0%,2M +2.7%,4M +1.7%,6M +1.2–1.4%,8M–10M +1%,≥14M ≤ 0.7%。第一轮的逐 kernel 计时给出同步循环的 CPU 气泡:2M 时 GPU 帧 3536 µs 对应 282.8 fps,而 CPU 侧只有 270.2 fps,气泡 ≈ 165 µs/步(4.6%)。论文中引用单卡强扩展参考值时,应使用 **V5 同步** 列(与双卡 K=1 参考的测法一致)或注明在飞深度。

## 诊断与修复

### 排除:`SHARING_MODE_CONCURRENT`

V5 为了让传输队列直接 DMA,把 12 个 set-0/1/3 缓冲声明为 CONCURRENT(compute + transfer 两个队列族),文档一直估计其代价"3–5%"。用新增的诊断开关 `V5_CONCURRENT_BUFFERS=0`(仅单卡可用,全部改为 EXCLUSIVE)做 A/B(1 次,同一卡,同窗口;对照为第一轮 V5 的 3 轮均值):

| 尺寸 | 在飞 | CONCURRENT | EXCLUSIVE | 差 |
|---|---|---|---|---|
| 2M | 1 | 259.0 | 258.6 | −0.2% |
| 2M | 2 | 265.5 | 265.9 | +0.1% |
| 8M | 1 | 67.2 | 66.9 | −0.4% |
| 8M | 2 | 67.8 | 68.6 | +1.2% |
| 32M | 1 | 17.6 | 17.60 | 0 |
| 32M | 2 | 17.7 | 17.67 | 0 |

共享模式最多贡献 ~1%(仅 8M 2 帧在飞一点),不是主因。数据 `docs/single_gpu_baseline_20260923/exclusive_ab/`。

### 定位:逐 kernel GPU 时间戳(`_run_kernel_breakdown.py`,同步循环,每步 6 个 BOTTOM_OF_PIPE 时间戳,预热 1000 + 计时 2000 步,defrag 帧剔除)

| kernel(µs/步) | 2M V0 | 2M V5(修复前) | Δ | 8M V0 | 8M V5(修复前) | Δ |
|---|---|---|---|---|---|---|
| predict | 94.4 | 94.1 | 0 | 493.7 | 493.9 | 0 |
| update_voxel | 35.6 | 35.6 | 0 | 336.3 | 335.3 | 0 |
| correction | 991.1 | 982.5 | −0.9% | 3888.8 | 3880.2 | −0.2% |
| density(含 scratch→primary 拷贝) | 1089.1 | 1139.8 | **+4.7%** | 4214.6 | 4431.3 | **+5.1%** |
| force | 1325.6 | 1406.0 | **+6.1%** | 5136.3 | 5488.8 | **+6.9%** |
| GPU 帧总计 | 3535.8 | 3657.9 | +3.5% | 14069.7 | 14629.5 | +4.0% |

**全部差异来自 density 和 force**,predict、update_voxel、correction 逐 µs 一致。三个邻居遍历 kernel 的内层循环源码逐行相同;V5 新增的 band/mode/own-range 逻辑在单卡下全是 spec 常量,被 DCE;缓冲区限定符两边相同。唯一的结构差异是 `voxel_id` 编码:V0 是 x 最快(`id = x + y·NX + z·NX·NY + 1`),V5 为了让 x 列 slab 成为连续的 id 区间改成 x 最慢(`id = y + z·NY + x·NY·NZ + 1`)。数据 `docs/single_gpu_baseline_20260923/kernel_breakdown/`。

### 确认:对照实验(2M,同一卡,逐 kernel µs/步;`docs/single_gpu_baseline_20260923/encoding_ab/`)

| 实验 | correction | density | force | GPU 帧 | CPU fps |
|---|---|---|---|---|---|
| V0 基线(x 最快编码,dx 最内层) | 991 | 1089 | 1326 | 3536 | 270.2 |
| V5 修复前(x 最慢编码,dx 最内层) | 983 | 1140 | 1406 | 3658 | 261.8 |
| E1 V5 用本机 glslc 重编译 | 978 | 1136 | 1396 | 3640 | 264.9 |
| **E2 V5 改用 V0 的 x 最快编码** | 992 | **1091** | **1325** | **3538** | 272.2 |
| **E3 V0 改用 V5 的 x 最慢编码** | 984 | **1146** | **1402** | **3662** | 263.5 |
| **E4 V5 保留 x 最慢编码,邻居循环改成 dy 最内层** | **962** | **1079** | **1295** | **3466** | **277.6** |

E2/E3 互换编码后两者的数字完全对调,说明差距 100% 来自编码,与工具链无关(E1)。根因是**循环嵌套与编码不匹配**:三个邻居 kernel 的循环是从 V0 继承的 `dz → dy → dx(最内)`,在 x 最快的 V0 里最内层遍历的 3 个邻居 voxel 在内存里相邻;而 V5 内存里最快的轴是 y,最内层却仍然走 x,每一步都跳过一整列 voxel。E4 把嵌套改成 `dx → dz → dy(最内)`(遍历同一个邻居集合,只改求和顺序)后,V5 不但追平 V0,还快了 2%(8M:V5 13920 µs vs V0 14070 µs,快 1.1%)。

### 修复(提交 `f9c660e`)

`experiment/v5/shaders/{correction,density,force}.comp` 的邻居循环改为 y 最内层,重新编译的 SPIR-V 一并提交。验证:
- 单卡 2M/8M drift = 0;修复后全场重测 120 次 drift = 0;
- 2×5090 双卡 2M(w = 1.0,4000 步)409 fps,总粒子数与期望完全一致;
- 数值等价性电池(K=1,1,2 校准 + K=2)`ALL PASS`(`encoding_ab/equivalence_2m_dy_inner_k2.log`);
- K=4 链(4 slab 跑在 2 张卡上)在本机 Windows 上用旧 shader 和新 shader 都会卡在传输 worker 的 timeline 等待上(第 159 / 37 帧),是预先存在的问题,与本修改无关(`logs/single_baseline_20260923/encoding_ab/k4_{old,new}_shaders.log`)。

规则(写进 CLAUDE.md):**邻居循环的最内层必须沿 voxel 编码里变化最快的轴。**

## 与旧数据的关系

- V5 单卡的 2026-06-19 曲线数据(`logs/scaling_2x5090.jsonl`,同步循环,带 GPU 时间戳,预热 5000)为 1M 506.5、2M 262.8、8M 68.1、32M 17.7 fps;第一轮(修复前)同步模式为 505.0 / 259.0 / 67.2 / 17.6,一致(≤ 1.5%,差异来自时间戳与预热长度)。修复后为 522.7 / 269.7 / 70.7 / 18.4,即旧曲线里所有 V5 单卡参考值系统性偏低 3–4%;双卡数字同样受益于修复(kernel 共用),若要更新论文里的 η,单卡参考与双卡都应在修复后的代码上重测。
